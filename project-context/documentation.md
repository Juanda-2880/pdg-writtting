## Introduction

The Artificial Intelligence and Software Architecture Laboratory (IAsLab) of Universidad Icesi manages computational infrastructures used in academic and research projects in critical areas such as data science and artificial intelligence. The laboratory operates within the Department of Computing and Intelligent Systems (*Departamento de Computación y Sistemas Inteligentes*) of the Barberi Faculty of Engineering, Design and Applied Sciences (authors, 2026-10-09).

Historically, the use of these resources faced barriers related to manual configuration and hardware underutilization, which limited the scalability and reproducibility of experiments.

To address this need, a web system was developed in a first phase, designed as a control plane that centralized the configuration, execution, and tracking of distributed training tasks. This development solved the initial problem by enabling automated and secure provisioning of processing nodes, integrating institutional security mechanisms such as SAAMFI for identity management.

However, the machine learning lifecycle (MLOps) extends beyond the training and experimentation stage. As the laboratory's projects advance, it becomes necessary to enable model deployment for consumption, ensure equitable hardware management as concurrency increases, and provide the system with technical observability. **This project builds the platform that provides those capabilities** (framing corrected by the authors 2026-09-12, after the tutor's observation on 2026-09-09: *"puede que ustedes no hagan eso, sino que ustedes van a directamente levantar la base del sistema web de orquestación"*). Earlier drafts described the work as maturing or extending the web system built in the first phase; that was wrong. The prior system is a separate degree project under the same macro-project, and no component of it is inherited, extended or refactored here. The only preexisting institutional component this project integrates with is SAAMFI, purely as an identity provider.

### Institutional antecedents: hardware access and manual deployment (from tutor and lab communications, 2026-08-26 and 2026-09-04)

> Recorded from `project-context/meetings/2026-08-26-tutor-arquitectura.md` (tutor, ADR-014 answers) and `project-context/meetings/2026-09-04-alejandro-elicitacion.md` (IAsLab staff member Alejandro Muñoz Bravo). Authorized by the authors (2026-09-12) for use as project fact per `CLAUDE.md` rule 9.

Before this first phase, the IAsLab lacked a standardized platform for managing access to its computing equipment. Access was granted via VPN (such as ZeroTier) and administrative permissions upon individual request, allowing access to students in related courses (such as Software Engineering IV), IAsLab members, and professors or students who submitted a request ("si un estudiante o profesor solicitaba acceso se le daba", tutor feedback, 2026-09-17). However, this provisioning workflow was entirely manual and often involved lengthy wait times before requests were processed and approved. The lack of an automated provisioning mechanism discouraged continuous utilization by the broader academic community, leading many to resort to external services such as Google Colab or forgo specialized computing, which produced sustained underutilization of the installed hardware ("realmente no usan la infraestructura de acá", tutor, 2026-08-26). The economic-equity argument points the other way: because not every student can sustain the cost of a commercial cloud-computing subscription, the laboratory has reason to open its own infrastructure to more users, not to restrict it (corrected by the authors 2026-09-13; the earlier wording read "Behind the restriction sat an economic-equity rationale", which inverted the tutor's point: "muchas personas pueden no pagar, no tienen las capacidades económicas para poder soportar la carga de, por ejemplo, pagar mensualmente un agente", 2026-08-26). As of the 2026-09-04 meeting, the laboratory's own use of its infrastructure remains at the experimentation stage, not continuous production use ("estamos simplemente...haciendo experimentos, no...uso continuo o explotación directa", Alejandro Muñoz Bravo, 2026-09-04). No formal access-request logs are on file; this account reflects direct tutor and lab staff communications.

Separately, before this project the laboratory deployed models manually: installing candidate inference engines and packages via Python scripts run by hand, without any platform automating the process ("fue básicamente como la ejecución de un par de scripts y ya. No hicieron una plataforma ellos directamente", tutor, 2026-08-26). Building on that practice, the laboratory evaluated inference engines with its own benchmarking harness, a Python script driven by declarative YAML specifications that measures input/output tokens per second and end-to-end response time (Alejandro Muñoz Bravo, 2026-09-04). Based on those benchmarks, the laboratory concluded that a purpose-compiled build of llama.cpp, compiled specifically for the hardware in room 104M, lets them deploy the best-performing models among those tried, after vLLM failed to produce good results in the lab's own trials. The measured baseline is approximately 20 tokens per second, with 10 to 15 minute response times, across the room's 31 workstations.

## Problem Description

Although the first phase of the project mitigated the operational bottleneck associated with model training and basic task orchestration, the current system presents limitations regarding the productive stages of the artificial intelligence lifecycle and the progressive scaling of its users.

Currently, researchers using the platform do not have a mechanism within the web system to configure and manage the distributed deployment and inference of previously trained models (especially large-scale architectures such as LLMs). This gap fragments the workflow and limits putting research into production. On the other hand, the growing adoption of the system creates a latent risk of monopolization of graphics processing units (GPUs), since the platform does not incorporate a governance system with quotas or formal role-based restrictions. Finally, its monitoring module lacks fine-grained telemetry, preventing administrators from observing exact infrastructure consumption metrics in real time.

> Reading note (propagado de la corrección de *Introduction*, 2026-09-12): the two paragraphs above keep the charter's original wording, which describes these gaps as limitations of "the current system". Per the correction in *Introduction*, the first-phase system is a separate degree project and is not extended here; the gaps are what the new platform this project builds must cover.

## Scope

- **High-level requirements:** The project will deliver the platform's frontend and backend, comprising: a telemetry panel with granular per-node metrics, an administrative quota module linked to the roles SAAMFI provides, and a deployment interface connected to a technology-agnostic inference orchestrator. (Corrected 2026-09-12: earlier wording said "the extension of the current frontend and backend", which presupposed a preexisting system with this scope. There is none.)
- **Architectural core (promoted by the authors 2026-09-13, from `meetings/2026-08-26-tutor-arquitectura.md` [38:22]):** the core of the project is the infrastructure and service layer underneath (orchestration, quotas, observability). The model-deployment module is **a use case** that integrates with and consumes that layer, not the centre of the project. Tutor's words: *"ese módulo de despliegue es como un caso de uso. Es un módulo que se integraría y que usaría el sistema que está por debajo que ustedes están planteando"*.
- **Exclusions:** No neural network architectures, proprietary AI models, or underlying mathematical algorithms will be developed. Migration to commercial public cloud providers (such as AWS, GCP, or Azure) is also not contemplated. **This project does not build model-training features** (that remains the sibling degree project's scope, under the same macro-project). Since 2026-09-13 the exclusion also covers governing, counting and observing training workloads (authors: *"no se incluye la parte de soportar entrenamiento"*).
- **Scope clarification (confirmed by the authors, 2026-09-12; WITHDRAWN by the authors, 2026-09-13):** the platform does not support training workloads; the quota system governs the inference workloads it deploys, and the observability module reports node state without classifying workloads. `requirements.md` §3.1 (`Sin compromiso`) covers training support and is out of scope for this document. Former text, kept for history: the reservation-based quota/governance system and the observability module must **not assume every GPU-node workload is inference**. Training jobs run on the same physical hardware (the sibling project's control plane schedules them on the same 31 workstations in room 104M), and today they run **ungoverned** — this is itself part of the monopolization risk described in Problem Description above. A quota system that only accounts for inference sessions and stays blind to training jobs would leave that risk half-solved. See `requirements.md` §3.1.
- **Constraints:** The software will run strictly on-premise, operating within the bandwidth and physical capacity limits of the units installed in the laboratory. **The platform targets compute nodes with NVIDIA GPUs exclusively (authors, 2026-09-20):** every worker node the laboratory provides is an NVIDIA-equipped workstation, and the provisioning and telemetry layers depend on the NVIDIA GPU Operator and on the DCGM exporter, which read metrics that live in NVIDIA card firmware. Accelerators from other vendors are out of scope, and no capability of the platform is designed to be portable to them. **The cluster is deployed first in room 104M and its configuration must allow the deployment to be extended to other laboratory rooms (authors, 2026-09-21, from the tutor's review of `requirements.md`).** **Inference runs on a single node today because the room network does not sustain cross-node distribution; the platform must be prepared to enable distributed deployment across nodes through Ray when the infrastructure allows it (authors, 2026-09-21).**
- **Assumptions:** Uninterrupted availability of IAsLab clusters for testing is guaranteed, and the SAAMFI authentication service will remain persistent.
- **Post-project support (promoted by the authors 2026-09-13, from `meetings/2026-08-26-tutor-arquitectura.md` [9:27]):** once the project ends, support and maintenance of the platform are the IAsLab's responsibility (laboratory staff and monitors), not the authors'. Tutor's words: *"usted no debería preocuparse la parte de soporte posterior"*.

## Expected Results

As a result of this project, the IAsLab ORCHID platform is expected to be delivered, capable of supporting end-to-end MLOps operations within Universidad Icesi. The platform will allow users to interactively deploy generative models or other advanced architectures, while training runs keep being submitted through the sibling project's control plane and remain outside this platform's governance. At the same time, laboratory administrators will be provided with strict and observable control over hardware through automated quota schemes, ensuring that equipment is not overloaded and that an equitable service is provided to the university's students and professors, identified by the roles SAAMFI provides.

Additionally, the platform's interface (propagado de ADR-027, 2026-09-12: no prior IAsLab interface exists; formerly "the improved interface") and in-depth monitoring will drastically reduce cognitive and administrative burden.

## Decisions of 2026-11-07 (authors)

Source: the authors' instructions given directly in session on 2026-11-07, checked against the implementation repository (`backend/docs/requirements.md`, `backend/docs/estado.md`, `backend/docs/decisions/0038-plano-control-tres-servidores.md`).

- **Control plane: three nodes.** The final cluster has three control-plane nodes on physical machines of the laboratory, not one (R3-01, R3-02). The POC reproduces them as three virtual machines on a single physical server. The laboratory PCs are switched on and off without notice (confirmed by the authors, 2026-11-07), so no single PC can hold the control plane; with three nodes the loss of one does not stop it.
- **Schedule: the cluster is deployed in room 104M in December 2026.** In October and November 2026 the work runs on a proof-of-concept (POC) prototype: eight virtual machines on a laboratory server (three control, three service and two compute nodes without GPU). The phases of the development and their durations do not change; only the place where the cluster is first deployed moves to December.
- **Model deployment requires a permission granted by the administrator.** A user deploys a model only when the administrator has granted the permission to deploy models. Reason: protect the shared resources of the rooms.

- **Non-language workloads: weights only.** A non-language workload is delivered as a weights file in a format served by an engine of the catalogue, without a server of its own (R3-27).

## POC status and implementation progress (as built, 2026-11-07)

Source: the implementation repository (`backend/docs/estado.md`, `backend/poc/docs/01` to `04`, the specs `001` to `060` with their `INTEGRACION.md`, the ADRs `0004` to `0046` and the as-built diagram `backend/docs/architecture/diagramas/13-poc-montado.drawio.png`, generated on 2026-10-26; it shows the state of that date). Recorded here so that the thesis cites a project fact, not a repository detail.

- **Scope of the POC.** The proof of concept (POC) runs on a single physical server of the laboratory, `orchid-server`, with 60 GiB of RAM. The cluster is simulated on eight virtual machines: three control-plane nodes, three service nodes and two compute nodes **without GPU**. Each model is served on one compute node. The POC is a prototype: its implementation can change before the cluster is deployed in room 104M.
- **Cluster.** Kubernetes v1.36.5 with RKE2 on three servers (etcd with quorum of 2 of 3 and kube-vip), Canal as CNI, Sealed Secrets, MetalLB for the fixed entry address, and Envoy Gateway.
- **Delivery and storage.** Argo CD v3.5.6 applies the configuration versioned in Bitbucket on `master` (19 applications, all synchronized and healthy on 2026-11-02). Storage uses Longhorn, Garage as the object store for model weights, zot as the container registry, and CloudNativePG for the database.
- **Governance and workloads.** Kueue v0.20.0 admits each workload against a quota per user (ClusterQueue, LocalQueue and Cohort). KubeRay 1.7.1 with Ray 2.59.0 runs as a `RayService`. Pod Security restricted and validating admission policies apply to user namespaces.
- **Engines.** Engines are chosen by model format (ADR 0030): GGUF weights with llama.cpp (official image, CPU in the POC) and safetensors weights with vLLM 0.32.0 (CPU, eager mode). A proxy adapter (ADR 0042) measures time to first token and inter-token latency for the Ray variant. The deployment flow is: the API checks that the deployment fits the user's quota and writes it as a cluster resource; the operator watches that resource and generates the engine workload, the weights volume, the service and the network route; Kueue admits it or keeps it waiting; the scheduler places it on a compute node; an init container copies the weights from Garage to the node's volume unless they are already there; the engine loads them; Envoy Gateway publishes the route of the model. The visible phases are queued, admitted, fetching weights and running. The API and the operator never talk to each other directly; both talk to the cluster API, so a request is not lost if the operator is down (source: `backend/ESTADO-ORCHID-APP.md`, «El flujo de un despliegue»).
- **Platform components built.** A custom operator (`orchid-operator`) with the CRDs `Engine`, `Model`, `ModelDeployment`, `QuotaTemplate` and `Quota`; a weights importer that verifies size and SHA-256 for GGUF and safetensors formats; an API with local users and PostgreSQL; a minimal web interface; deployment logs read from Loki and filtered by user; a Grafana panel by model and deployment; model registration from the API and the web, with the Hugging Face token stored encrypted (AES-256-GCM).
- **Verified behaviour in the POC.** Admission by quota with waiting when there is no capacity; recovery of quota by preemption, with the deployment state showing who was preempted and when; an out-of-memory event in one workload without affecting its neighbour; rejection of non-compliant deployments by admission policies; recovery of the weights copy after the loss of a node.
- **Measurements in the POC (CPU only, not a performance evaluation).** Qwen3-0.6B in GGUF Q8_0 with llama.cpp on CPU: between 15 and 17 tokens per second (the two repository documents differ by this range; the thesis uses the range). Qwen3-0.6B with vLLM on CPU: about 3 tokens per second with two cores. The Ray variant adds 2.4 % of latency over direct llama.cpp for the same output. No load test has been run yet.
- **Architectural adjustments caused by the hardware.** (a) The control plane moved from one node to three servers (ADR 0038); the decision came from the inventory of room 205, where all PCs were switched on the same day and use mechanical disks. (b) Serving moved from KServe to KubeRay (ADR 0016), and a `Deployment` under Kueue was fixed as the baseline (ADR 0029). (c) Because the POC server has no GPU, the engines run on CPU, and GPU validation waits for the room.
- **In implementation, not yet complete.** Integration with SAAMFI (Q-002): today the POC uses a local identity provider with the same contract. GPU operator, DCGM exporter and the verification of metrics on the room's GPUs. Role-based priority and quota reservations, pending verification (decision D-08 in the implementation repository). Backups outside the cluster and failover tests of the databases. Long-term retention of metrics in Thanos is configured but not yet confirmed to upload blocks.
- **Hardware of the room (reference).** The room's GPU, observed read-only on 2026-10-22, is an NVIDIA RTX 4500 Ada Generation with 24 GB of VRAM, in 30 PCs. One PC (104m30) has no NVIDIA GPU.

### POC sprints and challenges (as built, 2026-11-07)

- **Two stages of the prototype.** The first stage, from 17 to 26 October 2026, built the cluster foundations. The second stage, from 26 October to 7 November 2026, built the model service and the governance. Both stages fall within sprints 2 (12 October to 1 November) and 3 (2 to 22 November) of the schedule. The prototype built minimal versions of components that the schedule completes in later phases; the phases and their order do not change.
- **Engine resources.** The llama.cpp engine runs with 2 CPU; the vLLM engine runs with 2 CPU on the POC.
- **Challenges in the first stage.** The operating system of the virtual machines did not detect their disk or network, because the machine definition did not enable the advanced configuration and power interface (ACPI) through which the system discovers its devices; it was enabled in the definition. All nodes carried scheduling reservation marks (taints), so the installation jobs of the base components found no node to run on; the service nodes were left without taint and identified only by a label (ADR 0024). A single control-plane server would leave the cluster without API access if it failed, and the laboratory PCs are switched on and off without notice; the control plane uses three servers (ADR 0038).
- **Challenges in the second stage.** vLLM exhausted memory during its warm-up phase; it runs in eager mode, which skips that warm-up. The Argo CD autoscaler had no memory requests to compute its usage; the requests were fixed. The server has 60 GiB of memory, so each component declares the memory and processor it requests and its maximum limit, and the total stays within the capacity of the server.
- **Identity during the POC.** The integration with the institutional identity provider SAAMFI is in implementation. Meanwhile the POC uses a local identity provider that exercises the flow of roles, authentication and permissions end to end.
- **How a user deploys a model in the POC (user's view).** The administrator first registers the model in the catalogue, from the identifier of an external model repository; the platform shows a preview, the importer downloads the weights, verifies them and stores them in the object store, and a model in use cannot be deleted. The administrator also grants each user the permission to deploy. The user then picks a model from the catalogue in the web interface, chooses one of the enabled engines and, as an advanced option, the node; the deployment goes through the phases queued, admitted, fetching weights and running (about one minute in the POC), and is published at an address formed by the user name and the deployment name, with an API compatible with OpenAI. The user can follow the logs of the deployment, stop it, start it again and delete it; the administrator sees and manages the deployments of every user (source: `backend/docs/estado.md`, rows of the minimal web interface, deployments API, model registration and administration of deployments; `backend/ESTADO-ORCHID-APP.md`, «El flujo de un despliegue»).
